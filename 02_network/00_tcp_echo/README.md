# TCP 에코 서버를 만들며 배운 것

에코 서버는 클라이언트가 보낸 데이터를 그대로 돌려준다. 동작은 단순하지만, 구현하려면 소켓이 무엇을 가리키는지, 연결과 데이터 전송이 어떻게 다른지, TCP에서 데이터를 어디까지 읽어야 하는지 알아야 한다.

이번 코드는 IPv4 TCP로 클라이언트 하나와 통신한다. [server.c](server.c)는 받은 바이트를 돌려주고, [client.c](client.c)는 자신이 보낸 길이만큼 응답을 모아서 출력한다. [htonl_test.c](htonl_test.c)는 정수의 값과 메모리에 저장된 바이트 순서의 차이를 확인하기 위한 코드다.

## 1. 소켓은 포트 번호가 아니다

```c
int server_fd = socket(AF_INET, SOCK_STREAM, 0);
```

`socket()`은 커널에 통신용 소켓을 만들고, 프로그램이 그것을 사용할 수 있도록 파일 디스크립터를 반환한다. `server_fd`에 들어가는 정수는 IP 주소나 포트 번호가 아니라, 이 프로세스에서 소켓을 참조하는 번호다. 실패하면 `-1`을 반환한다.

| 인자 | 이번 코드에서의 의미 |
| --- | --- |
| `AF_INET` | IPv4 주소 체계 사용 |
| `SOCK_STREAM` | 연결을 통한 바이트 스트림 통신 |
| `0` | 이 조합의 기본 프로토콜 사용. 여기서는 TCP |

IP 주소와 포트는 이후 `bind()`나 `connect()`에 전달하는 주소 구조체에 들어간다. 소켓 생성과 주소 설정은 서로 다른 단계다.

## 2. 연결을 받는 소켓과 데이터를 주고받는 소켓

서버 코드에는 `server_fd`와 `client_fd`가 따로 있다.

```c
listen(server_fd, 5);
client_fd = accept(server_fd,
                   (struct sockaddr *)&client_addr,
                   &client_addr_len);
```

`server_fd`는 새 연결을 받는 리스닝 소켓이다. `accept()`는 연결 하나를 꺼내 **새로운 연결 소켓**을 반환하고, 이후 `recv()`와 `send()`에는 이 `client_fd`를 사용한다. 기존 리스닝 소켓이 연결 소켓으로 바뀌는 것은 아니다.

```text
서버 프로세스                          클라이언트 프로세스

server_fd ── 새 연결을 받는 역할
                 │
              accept()
                 │
client_fd ◀══════ TCP 연결 ══════▶ sockfd
          송신과 수신 모두 가능
```

클라이언트가 세 명이라면 서버에는 보통 리스닝 소켓 하나와 연결 소켓 세 개가 필요하다. 서버가 `socket()`을 한 번만 호출하더라도, `accept()`가 연결마다 소켓을 추가로 만든다.

모든 클라이언트가 같은 서버 포트에 접속해도 된다. TCP 연결은 양쪽 IP 주소와 포트의 조합으로 구분되므로, 같은 서버 포트를 사용한다고 같은 연결이 되는 것은 아니다.

또한 소켓 하나로 송신과 수신을 모두 할 수 있다. 송신용 소켓과 수신용 소켓을 따로 만드는 구조가 아니다.

## 3. 서버와 클라이언트의 연결 과정

```text
서버                                  클라이언트
socket()                              socket()
   │                                     │
bind()                                   │
   │                                     │
listen()                                 │
   │                                     │
accept()에서 연결 대기  ◀────────────  connect()
   │                                     │
연결 소켓 반환                         연결 성공
   │                                     │
recv()                 ◀────────────  send()
send()                 ────────────▶  recv()
   │                                     │
close()                               close()
```

이 그림은 프로그램의 흐름을 나타낸다. TCP 연결 수립 자체는 커널이 처리하며, 서버 코드가 `accept()`를 호출하기 전에도 리스닝 상태라면 연결이 수립되어 대기할 수 있다.

`bind()`는 소켓에 로컬 주소를 지정하고, `listen()`은 연결 요청을 받을 수 있는 상태로 만든다. `listen(server_fd, 5)`의 `5`는 연결 대기열에 관한 값이지, 클라이언트 다섯 명을 동시에 처리한다는 뜻이 아니다. 동시 처리는 프로그램의 구조에 달려 있다.

현재 서버는 `accept()`를 한 번만 호출한다. 한 클라이언트와 통신하다 연결이 종료되면 리스닝 소켓까지 닫고 끝난다. 통신 루프가 있다고 해서 다음 클라이언트까지 계속 받는 서버인 것은 아니다.

## 4. 주소 구조체에 들어가는 것

```c
memset(&server_addr, 0, sizeof(server_addr));
server_addr.sin_family = AF_INET;
server_addr.sin_addr.s_addr = htonl(INADDR_ANY);
server_addr.sin_port = htons(PORT);
```

`sockaddr_in`은 IPv4 주소와 포트를 담는 구조체다. 먼저 0으로 초기화한 뒤 필요한 필드를 채운다.

서버의 `INADDR_ANY`는 로컬 IPv4 주소 하나만 지정하지 않고 연결을 받겠다는 의미다. 클라이언트가 접속할 목적지 주소를 뜻하지는 않는다.

반면 클라이언트의 `127.0.0.1`은 **클라이언트 프로그램이 실행되는 장치 자신**을 가리킨다. 클라이언트를 PC에서 실행하면 PC 자신이고, Jetson에서 실행하면 Jetson 자신이다. 서로 다른 장치 사이에서 통신하려면 서버 장치의 실제 주소를 사용해야 한다.

```c
inet_pton(AF_INET, SERVER_IP, &server_addr.sin_addr);
```

`inet_pton()`은 `"127.0.0.1"` 같은 문자열을 소켓 API에서 사용하는 이진 주소로 변환한다. 결과는 네트워크 바이트 순서이므로 여기에 다시 `htonl()`을 적용하지 않는다.

`bind()`와 `connect()`에 `(struct sockaddr *)`로 캐스팅하는 이유는 API가 여러 주소 체계를 공통 포인터 타입으로 받기 때문이다. 캐스팅 자체가 IPv4 주소를 다른 형식으로 변환하는 것은 아니다.

`accept()`의 `client_addr_len`은 입력과 출력에 모두 쓰인다. 호출 전에는 주소를 받을 공간의 크기를 알려주고, 호출 후에는 반환된 주소 길이를 전달받는다.

## 5. `htonl()`은 숫자를 바꾸려는 함수일까?

네트워크 바이트 순서는 big-endian이다. 여러 바이트로 된 정수를 보낼 때 상위 바이트부터 놓는 규칙이다. 호스트의 메모리 표현이 다를 수 있으므로, 주소 구조체의 포트와 IPv4 주소를 이 규칙에 맞춘다.

| 함수 | 방향 | 크기 |
| --- | --- | --- |
| `htons()` | host → network | 16비트 |
| `htonl()` | host → network | 32비트 |
| `ntohs()` | network → host | 16비트 |
| `ntohl()` | network → host | 32비트 |

여기서 `l`은 이 API에서 32비트를 뜻한다. 사용하는 시스템의 C `long` 크기가 얼마인지를 기준으로 동작하는 것은 아니다.

`htonl_test.c`의 `0x12345678`을 little-endian 환경에서 살펴보면 다음과 같다. 메모리 바이트는 낮은 주소부터 적었다.

| 구분 | 정수로 출력한 값 | 메모리의 바이트 순서 |
| --- | --- | --- |
| `host_value` | `0x12345678` | `78 56 34 12` |
| `htonl(host_value)` 결과 | `0x78563412` | `12 34 56 78` |

변환 결과를 호스트 정수로 출력하면 숫자가 뒤집힌 것처럼 보인다. 하지만 목적은 **메모리에 놓인 바이트를 네트워크 순서에 맞추는 것**이다. Big-endian 환경에서는 변환 전후가 같으므로, 위 표의 출력은 모든 장치에서 동일한 결과가 아니다.

문자열 전체에 `htonl()`을 적용하는 것은 아니다. 이번 에코 데이터는 입력받은 바이트 그대로 보내고, 정수 필드를 주고받는 프로토콜을 만들 때 각 필드의 크기와 바이트 순서를 정하면 된다.

## 6. TCP에는 메시지 경계가 없다

TCP는 순서가 있는 바이트 스트림을 제공한다. 애플리케이션에서 `send()`를 몇 번 호출했는지는 수신 측의 메시지 경계로 전달되지 않는다.

```text
보낸 쪽:  send("hello")  send("world")

받는 쪽에서 가능한 모습:
          recv() → "helloworld"
또는      recv() → "he"
          recv() → "llowor"
          recv() → "ld"
```

바이트 순서는 유지되지만, 어느 호출에서 몇 바이트를 받는지는 달라질 수 있다. `BUFFER_SIZE`가 1024라는 것도 한 메시지가 1024바이트라는 뜻이 아니다. 해당 배열에 담을 수 있는 크기일 뿐이다.

에코 서버는 받은 조각을 그대로 돌려주면 되므로 메시지 경계를 몰라도 동작한다. 하지만 채팅 서버는 어디까지가 한 메시지인지 알아야 한다. 줄바꿈을 구분자로 쓰거나, 메시지 앞에 길이를 붙이는 등의 규칙이 필요하다.

## 7. 왜 `send()`와 `recv()`를 반복할까?

### 요청한 길이와 실제 전송한 길이는 다를 수 있다

`send()`의 반환값은 이번 호출이 실제로 받아들인 바이트 수다. 요청한 길이보다 작을 수 있으므로, 코드에서는 이미 보낸 위치와 남은 길이를 갱신한다.

```c
send(client_fd,
     buffer + sent_total,
     received - sent_total,
     0);
```

예를 들어 100바이트 중 40바이트를 보냈다면, 다음 호출에서는 `buffer + 40`부터 남은 60바이트를 보낸다. 처음부터 다시 보내면 앞부분이 중복된다.

또한 `send()` 성공은 상대 프로그램이 데이터를 읽었다는 확인이 아니다. 상대의 처리 완료까지 확인하려면 애플리케이션 수준의 응답이 필요하다.

### 에코 클라이언트는 응답 길이를 미리 알고 있다

클라이언트는 `strlen(buffer)`로 보낸 길이를 기억하고, `received_total`이 그 길이에 도달할 때까지 수신한다. 자신이 보낸 만큼 그대로 돌아온다는 에코 규칙이 있기 때문에 가능한 방식이다.

이것을 일반적인 채팅 수신에 그대로 적용할 수는 없다. 채팅에서는 다른 사람이 보낸 메시지가 언제, 얼마나 올지 모르므로 별도의 메시지 경계 규칙과 수신 처리가 필요하다.

### 수신 결과는 바이트 수로 판단한다

이번처럼 수신 길이를 0보다 크게 지정한 TCP `recv()`에서는 다음과 같이 해석한다.

| 반환값 | 의미 |
| --- | --- |
| 양수 | 실제로 받은 바이트 수 |
| `0` | 상대가 송신 방향을 정상 종료했고, 읽을 데이터가 더 없음 |
| `-1` | 오류 발생. 구체적인 원인은 `errno`로 확인 |

상대가 송신만 종료하는 half-close도 있으므로 `0`이 항상 양방향 통신이 모두 불가능하다는 뜻은 아니다. 현재 코드는 이를 통신 종료 조건으로 사용한다.

## 8. 수신 버퍼는 자동으로 문자열이 되지 않는다

`recv()`는 바이트를 배열에 복사할 뿐, 끝에 널 문자 `\0`을 붙여주지 않는다. 따라서 수신 직후 무조건 `printf("%s", buffer)`로 출력하면 유효한 데이터 범위를 넘어 읽을 수 있다.

클라이언트는 다음과 같이 출력 길이를 제한한다.

```c
printf("Echo: %.*s", (int)received_total, buffer);
```

`%.*s`는 지정한 길이까지만 문자열을 읽는다. 다만 중간에 널 문자가 있으면 출력이 멈추므로 임의의 바이너리 데이터를 그대로 출력하는 방법은 아니다.

이 코드에서 `fgets()`는 공간이 허용되면 줄바꿈까지 저장하고, 끝에 널 문자를 붙인다. `strlen()`은 줄바꿈을 포함하지만 마지막 널 문자는 제외한다. 즉, 줄바꿈은 전송 데이터에 포함될 수 있고 문자열 종료용 널 문자는 보내지 않는다.

## 9. 현재 구현의 범위와 남은 과제

현재 소켓은 기본 블로킹 방식이다. 연결이 없으면 `accept()`에서, 데이터가 없으면 `recv()`에서 기다린다. `send()`도 송신 버퍼에 여유가 없으면 기다릴 수 있다.

따라서 한 실행 흐름으로 한 연결을 처리하는 구조를 이해하기에는 좋지만, 여러 클라이언트가 동시에 대화하는 서버로 쓰려면 구조가 달라져야 한다.

오류 처리에도 추가로 살펴볼 부분이 있다.

- 서버의 `send()` 오류 분기에서 `break`는 안쪽 전송 루프만 끝낸다. 바깥 수신 루프까지 종료하지는 않는다.
- 현재 `send()`의 플래그는 `0`이다. 끊긴 연결에 쓰는 과정에서 `SIGPIPE`가 발생하면 기본 동작으로 프로세스가 종료될 수 있다. Linux에서는 `MSG_NOSIGNAL` 등을 사용하고 전송 오류를 처리하는 방법이 있다.
- 현재는 `recv()`나 `send()`가 `-1`을 반환하면 오류로 처리한다. 시그널 때문에 중단된 `EINTR`처럼 재시도 여부를 판단할 경우는 구분하지 않는다.

이 항목들은 현재 코드에서 모두 해결했다는 의미가 아니라, 기본 송수신 흐름 이후에 보완할 지점이다.

## 10. 채팅 서버로 확장한다면

에코는 보낸 사람에게 돌려주지만, 채팅은 받은 메시지를 다른 연결에도 전달한다. 이 차이 때문에 연결 목록과 메시지 경계를 관리해야 한다.

지금까지의 개념을 멀티스레드 구조에 연결하면 다음과 같다.

| 대상 | 관리 방향 | 이유 |
| --- | --- | --- |
| 리스닝 소켓 | 연결을 받는 실행 흐름에서 관리 | `accept()`로 새 연결 소켓 생성 |
| 연결 소켓 | 클라이언트 연결마다 하나 | 각 소켓이 특정 상대와 연결됨 |
| 수신 버퍼 | 각 클라이언트별로 관리 | 서로 다른 연결의 데이터와 미완성 메시지를 구분 |
| 접속자 목록 | 스레드 사이에 공유하고 동기화 | 접속·퇴장·전송 대상 조회가 겹칠 수 있음 |
| 같은 연결로 보내는 작업 | 메시지 전체 전송을 직렬화 | 여러 스레드의 부분 전송이 서로 섞이지 않도록 처리 |

스레드 함수 안의 일반 지역 배열은 호출마다 별도로 생긴다. 다른 스레드에 그 배열의 주소를 넘기지 않고 담당 스레드만 사용한다면 수신 버퍼 자체에는 락이 필요 없다.

접속자 목록을 잠근 채 모든 소켓에 블로킹 `send()`를 하면 느린 클라이언트 때문에 다른 작업도 지연될 수 있다. 그렇다고 소켓 번호만 복사하고 락을 풀면, 전송 전에 다른 스레드가 소켓을 닫고 번호가 재사용되는 문제가 생길 수 있다. 락의 범위와 함께 연결을 언제 닫을지도 설계해야 한다.

멀티스레드라는 이유만으로 시그널 핸들러가 필요한 것은 아니다. 스레드 자원은 `pthread_join()`이나 `pthread_detach()`로 정리하며, 자식 프로세스 종료를 알리는 `SIGCHLD`와는 관계없다. 연결 종료 감지, 스레드 정리, 서버 전체 종료는 각각 구분해서 생각해야 한다.

이번 에코 코드에서 다음 단계로 가져갈 핵심은, **연결마다 소켓이 있고 그 소켓을 통해 흐르는 것은 경계 없는 바이트열**이라는 점이다. 그 위에서 메시지를 구분하고 여러 연결에 전달하는 규칙은 프로그램이 만든다.
